# 6. Deployment Documentation

[← Back to README](../README.md)

This project's `docker-compose.yml` is a **learning environment**, not a
production topology (dev-mode Vault, a hardcoded `root` token, secrets
generated fresh on every `up`). This document describes what changes on
the path to a real deployment, and why.

## Preparing the Server

- A Linux host (or managed container platform) with Docker, or a Python
  3.10+ runtime if deploying the app outside a container.
- A **separately operated, real (non-dev) Vault cluster** — in a real org
  this is almost never something the application team stands up
  themselves; it's a shared Platform-owned service. See
  [05-vault-setup.md](05-vault-setup.md) for what a real cluster needs
  (TLS, auto-unseal, HA storage backend, network restriction).
- DNS + TLS certificate for the app's own public endpoint, if it's
  internet-facing.
- Firewall rules: the app needs outbound access to Vault's port (443 in
  production, not the dev-mode 8200); Vault itself should not be reachable
  from the public internet.

## Installing Dependencies

Container path (recommended): build the existing `Dockerfile` — it
already installs everything from `requirements.txt`. No host-level Python
setup needed beyond Docker itself.

Bare-metal/VM path: install Python 3.10+, then
`pip install -r requirements.txt` inside a virtual environment, same as
[02-development-setup.md](02-development-setup.md).

## Deploying the Application

Build and push the image to your registry:
```bash
docker build -t your-registry/vault-demo-app:1.0.0 .
docker push your-registry/vault-demo-app:1.0.0
```
Then run it wherever your platform expects (a single `docker run`, a
Compose file without the dev-mode `vault`/`vault-init` services, a
Kubernetes Deployment like `k8s-examples/deployment-with-vault-injection.yaml`,
an ECS task definition, etc.) — the image itself doesn't change between
environments; only configuration does.

## Configuring Environment Variables in Production

The same variables as `.env.example`, but sourced differently:

| Variable | Dev (this repo) | Production |
|---|---|---|
| `VAULT_ADDR` | `http://vault:8200` (plain HTTP, dev container) | `https://vault.internal.example.com:8200` (TLS, real DNS) |
| `VAULT_AUTH_METHOD` | `approle` | `approle`, or Kubernetes/AWS IAM auth if the platform supports it (no secret to distribute at all) |
| `VAULT_ROLE_ID` / `VAULT_SECRET_ID` | Generated by `vault-init`, shared via a Docker volume | Provisioned by your Platform/DevOps team's own automation (Terraform, etc.), injected via your platform's secret store (K8s Secret populated by an external-secrets controller, AWS Secrets Manager, CI secret variables) — **never committed to a repo** |

The bootstrapping question — "how does the app get its *first* Vault
credential without a human typing it in?" — has no single universal
answer; it's solved differently per platform: Kubernetes auth
(ServiceAccount JWT, no secret at all), cloud instance identity (AWS
IAM/GCP), or a CI pipeline injecting a freshly-generated `secret_id` at
deploy time via the CI platform's own trusted identity. See
[07-devops-perspective.md](07-devops-perspective.md#vault-in-cicd).

## Connecting the Application to Vault

In production, `VAULT_ADDR` uses `https://`, and the client needs to
trust Vault's TLS certificate — either via a properly signed cert (public
CA or an internal CA already trusted by the host) or, if using a private
CA, `hvac.Client(..., verify="/path/to/ca-bundle.pem")`. This project's
`vault_client.py` doesn't currently take a `verify=` override — add one
for a real deployment rather than disabling verification.

## Running the Application

The dev container runs `python app.py`, which uses **Flask's built-in
development server** — explicitly not meant for production (Flask logs a
warning about this itself). For production, run under a real WSGI
server:
```bash
gunicorn --bind 0.0.0.0:5000 --workers 4 app:app
```
(`gunicorn` is already in `requirements.txt` for exactly this; it's
Linux/macOS-only, which is fine — the container image is Linux.) Override
the Dockerfile's `CMD` (not `ENTRYPOINT` — keep `docker-entrypoint.sh` so
AppRole credentials still get loaded) to the `gunicorn` command above for
a production image variant.

## Validation Steps

```bash
curl -f https://your-app.example.com/health
# {"status": "ok", "vault_reachable": true, "vault_authenticated": true}
```
A deploy pipeline should treat a non-`200` here as a failed deploy and
stop before shifting traffic — this is precisely what `/health` exists
for.

## Production Deployment Considerations

- **Never reuse the dev-mode root token** — production Vault access
  should always flow through a real auth method + least-privilege
  policy, per [05-vault-setup.md](05-vault-setup.md).
- **One AppRole role per application per environment** — not one shared
  role for every service; keeps blast radius and audit trails
  meaningful.
- **Short-lived `secret_id`s, delivered per-deploy** — not a long-lived
  value baked into an image.
- **Vault itself is a shared dependency with its own SLA** — if Vault is
  unreachable, this app's `/health` correctly reports degraded; design
  callers (load balancers, orchestrators) to react to that rather than
  serving traffic to a half-broken instance.

## Rollback Procedure

Application rollback is standard container rollback — redeploy the
previous image tag; the app is stateless and holds no data that needs
migrating back. Vault *configuration* (policies, roles, secret values) is
separate infrastructure state, not tied to an app release — don't
conflate "roll back the app" with "roll back Vault's config"; the latter
should be managed and versioned independently (Terraform + Vault provider
is the common approach) and rarely needs to move in lockstep with an app
deploy.

## Monitoring

- **App-level**: poll `/health` from your load balancer/orchestrator.
- **Vault-level**: Vault exposes a `/v1/sys/health` endpoint and
  Prometheus-format telemetry (`telemetry` stanza in Vault's config) —
  monitor seal status, request rates/latency, and token/lease counts.
  A sealed Vault or a spike in `403`s from this app's perspective are
  both actionable alerts.
- **Audit logs** (see [05-vault-setup.md → Security Hardening](05-vault-setup.md#security-hardening))
  are also a monitoring signal — unexpected paths being requested, or
  requests from an unexpected auth method, are worth alerting on.

## Logging

See [03-application.md → Logging](03-application.md#logging) for what
the app logs today. For production, ship logs (app + Vault audit device)
to a central aggregator (ELK/Loki/CloudWatch/etc.) as structured JSON
rather than plain text, and make sure secret *values* are never logged —
this project's logging deliberately logs paths and outcomes
(`"Permission denied reading %s"`) but never the secret data itself.

## Troubleshooting Deployment Issues

| Symptom | Likely cause |
|---|---|
| `/health` returns 503 immediately after deploy | New instance's `VAULT_ROLE_ID`/`VAULT_SECRET_ID` weren't provisioned/injected before the container started |
| Works locally, fails in prod with a TLS error | `VAULT_ADDR` uses `https://` but the client doesn't trust Vault's certificate — see [Connecting the Application to Vault](#connecting-the-application-to-vault) |
| Intermittent `403`s under load | A shared, low-TTL token expiring under concurrent requests without every request path going through `_ensure_authenticated()` — audit that all call sites do |
| Fine at deploy time, breaks hours later | `secret_id` had a short TTL/limited uses and nothing renews or re-provisions it — check `secret_id_ttl`/`secret_id_num_uses` on the AppRole role |
